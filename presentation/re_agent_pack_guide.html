Before You Start
Four things to have in place before running the installer
🖥
VS Code

Any recent version. The agents run as VS Code GitHub Copilot agents and must be selected from the Copilot chat agent dropdown.

🤖
GitHub Copilot

Copilot Chat with agent mode enabled. Agents live in .github/agents/ — VS Code reads them automatically.

📂
Your project folder open

Run the installer from the root of the project you want to analyse. The agents will read source files relative to that root.

🔧
curl or wget

The one-line installer uses curl or wget to pull files from GitHub. Both are standard on macOS and Linux.

Installation
One command — run from the root of the project you want to analyse
Terminal — run from your project root
# One-line install
bash <(curl -sSL https://raw.githubusercontent.com/sasCapDev/re-agent-pack/main/install.sh)

# After the agents are installed, baseline your source files:
bash pipeline/scripts/update-checksums.sh

Configuration
The only file you edit — generated by project-scanner at Step 0, then reviewed by you
Project Name / Company / System Description
Project Identity

Name the project, company, and one-sentence description of the system. Agents use this to frame all output — it appears in document headers and context sections.

Subdomain in Scope
What this run covers

Describe the specific screens and flows being analysed. Agents will stay within this boundary — they do not widen scope beyond what is declared here.

All Source Files
Source file list

Full list of files for agents to read. Auto-populated by project-scanner. Add or remove files before Step 1 if the scanner missed anything. Relative paths from project root.

Legacy Technology Stack
What the codebase is built on

Frontend, backend, integration layer, external services. Agents use this to frame technical findings and candidate API sections correctly.

Modernisation Target
What you're building towards

Target frontend, API layer, database, and integration stack. The dependency-mapper and document-publisher use this to produce candidate architecture estimates.

Document Prefix
Output file naming

Used for project identification in the Publication Contract. Output files use fixed names: Reverse_Engineered_Business_Requirements.md, Architecture_Flow.md, etc.

One file, every run.  Every agent reads RE_AGENTS_CONFIG.md before doing anything else. This is the only file you edit when deploying the pack to a new project — the agents adapt to whatever you put here.
The 9-Step Pipeline
Click any step to see the agent, the exact prompt to paste, and what it produces
  • 0
    project-scanner
    Scan the workspace and generate RE_AGENTS_CONFIG.md
    ▾
    PROMPT
    Scan this project workspace and generate RE_AGENTS_CONFIG.md.
    Produces
    • RE_AGENTS_CONFIG.md at project root — auto-filled from workspace scan
    • Fields marked [REVIEW: ...] need human input before Step 1
    • In batch mode (30+ dialog files): also generates RE_AGENTS_CONFIG_MASTER.md and per-subdomain configs
    • Initialises artifacts/session_state.governance.md — shared state read by every subsequent agent
    • On re-run: selective merge only — source file list always refreshed; manually curated fields preserved unless still [REVIEW: ...]. Shows diff summary and waits for confirmation before writing.

    After Step 0, run: bash pipeline/scripts/update-checksums.sh

  • 1
    analysis-planner
    Assess coverage and recommend what to run next
    ▾
    PROMPT
    Assess current artifact coverage and recommend which agent to run next.
    Produces
    • Coverage counter summary — actual vs estimated for each artifact type
    • Source file diff — compares current checksums against previous run's snapshot (source_checksums_prev.governance.md); reports Added / Modified / Unchanged per file
    • Recommended next agent using a three-priority stack: (1) source file changes override all — new UI files → screen-analyzer, new logic files → rule-extractor; (2) pipeline sequence from session_state.governance.md last completed step; (3) coverage percentages as fallback only
    • No artifacts modified — read-only assessment
  • 2
    screen-analyzer
    Analyse screens, fields, and controls
    ▾
    PROMPT
    Inspect the screens in scope and update the screen inventory, field dictionary, and traceability matrix.
    Produces
    • artifacts/generated_screen_inventory.md — screen name, purpose, user type, key controls
    • artifacts/field_dictionary.md — every DDX field, control type, constraints, audit trigger
    • artifacts/traceability_matrix.md — UI layer rows added
  • 3
    rule-extractor ★ core step
    Extract business rules into the rule register
    ▾
    PROMPT
    Extract business-rule candidates from all source files in scope.
    Produces
    • artifacts/rule_register.governance.md — each rule as a card with: Screen, Action, Rule statement, Rule type, Functional Area, Evidence (file::function), Grounding, Confidence
    • Deduplication check — compares each candidate against the existing rule register by Screen + Action + core constraint; matching cards get their Evidence/Grounding/Notes updated in place rather than creating a duplicate
    • Coverage gap table — functions with rule-like keywords that have no card yet
    • artifacts/traceability_matrix.md — business rules rows added

    Functional Area is tagged at extraction time (e.g. Loan Search — Premium Rating, Client Management — Field Validation) — no manual categorisation needed later.

  • 4
    dependency-mapper
    Trace actions to services, gateways, and candidate APIs
    ▾
    PROMPT
    Trace the main user actions in scope and map their service, repository, and gateway dependencies.
    Produces
    • artifacts/screen_action_api_estimation.md — button click → handler → service → adapter → TME mnemonic → Tandem program + candidate REST API
    • artifacts/service_decomposition.md — candidate service groupings aligned to modernisation target
    • artifacts/traceability_matrix.md — action dependency and integration rows added
  • 5
    reviewer
    Grounding review — verify evidence and governance readiness
    ▾
    PROMPT
    Review all reverse-engineering outputs for overclaims, weak grounding, and governance readiness.
    Produces
    • Rule count sanity check — actual rule count vs expected minimum by file layer (threshold: 70%)
    • Evidence resolution check — every file::function citation verified to exist; unresolved references downgraded to [unresolved]
    • Functional Area completeness check — flags any card missing or unconfirmed Functional Area before publication
    • Coverage gap check — flags functions with rule-like keywords but no card
    • Any [placeholder] items counted and flagged for FRD block
  • 6
    analysis-planner
    Rerun scoping — identify what needs re-analysis after the governance review
    ▾
    PROMPT
    Re-evaluate only the rules and mappings that are flagged as Priority review or that remain ambiguous.
    Produces
    • Targeted rerun scope — only impacted rules and artifacts, not a full re-run
    • Entry written to artifacts/re_run_log.governance.md
    • File-type → artifact impact mapping: modified UI files flag screen inventory; modified rules files flag the rule register; modified gateway files flag service decomposition
    • List of which agents to rerun and what each should focus on

    Skip this step if the governance review flagged no rules for rerun.

  • 7
    document-publisher
    Generate all six final deliverables from the artifact set
    ▾
    PROMPT
    Generate all six final deliverables from the artifact set.
    Produces (in docs/final_output/)
    • Reverse_Engineered_Business_Requirements.md — rules grouped by Functional Area with a Review Priority column; structured Traceability Summary table
    • Reverse_Engineered_Technical_Specification.md — same grouping with full evidence citations for developers
    • Architecture_Flow.md — Mermaid business/technical flow diagrams (7 sections incl. Legacy→Modern mapping)
    • Forward_Engineering_Modernization_Blueprint.md — AI-consumable UI/API/DB specs for code generation
    • Rendering_Handoff.md — paste into Claude, ChatGPT, or Gemini to generate the 4 polished Word documents (Business Requirements, Technical Specification, Architecture Flow, Modernization Blueprint)
    • Publication_Contract.json — machine-readable manifest with functionalArea field; grounding statistics for Go/No-go check

    docs/final_output/ is gitignored — client deliverables stay out of the repository.

  • 8
    reviewer
    Publication sign-off — Go / No-go on the final documents
    ▾
    PROMPT
    Review the final output documents for publication readiness and give a Go / No-go.
    Produces
    • Reads Publication_Contract.json grounding statistics
    • No-go if any [placeholder] appears unqualified in the FRD — hard block
    • Go with advisory notes if [inferred] items are within acceptable bounds
    • If No-go: fixes required, re-run Step 7

Resetting the Pipeline
Two modes — choose based on whether you want to show the full pipeline run or just the governance review flow
--governance
Reset governance files only — keep analysis artifacts
bash pipeline/scripts/reset-artifacts.sh --governance

Clears the rule register governance state and ambiguity log back to the committed baseline. Analysis artifacts (screen inventory, field dictionary, traceability matrix, rules) are preserved.

Use this when you want stable, predictable content — the analysis is already done, and you want to show the Step 5 governance review and Review Priority flagging without re-running Steps 2–4.

--full
Full reset — restore to clean baseline
bash pipeline/scripts/reset-artifacts.sh --full

Restores all artifacts to the committed baseline snapshot. Agents will regenerate everything from Step 1 onwards — content is correct but phrasing varies slightly between runs.

Use this when you want to run the complete pipeline from scratch and show the full extraction process live.
